Use cases

Code You Did Not Write, Running on Your Machine

Every one of these has the same shape: something needs to execute, you cannot fully vouch for it, and wrapping it in a container is either too slow, too privileged, or not precise enough. These are the policies teams actually deploy.

AI Agents and Tool Execution

An agent that can run shell commands is, by construction, an arbitrary code execution primitive driven by a model. It needs a workspace it can write to, one or two API endpoints, and nothing else. Handing it a container means handing it a container's whole worldview, including whatever credentials sit in the environment.

Sandlock inverts that. The agent gets exactly the paths and exactly the endpoints you name. The API key never enters the agent's address space at all: it lives in the supervisor, and is attached to the outbound request in the proxy after the ACL check has already passed.

HTTP-level rules, not just host:443. Allow one method on one path.
Zero-config HTTPS interception. Sandlock generates an ephemeral CA, keeps the private key in memory, and splices the public cert into the trust bundles you name.
Credential stripped from the child. With env:VAR the variable is removed from the agent's environment, so it cannot read the key back out.
Runtime policy. A callback can revoke network access or deny a path the moment the agent finishes starting up.
GPU selection is a boundary. --gpu 0 makes the other device nodes unopenable, not merely hidden.
Also available as

An MCP server exposing sandboxed shell, Python, and file tools to Claude Desktop, Cursor, and any other MCP client, with a fresh sandbox per call.

Agent with one endpoint and no key 
$ sandlock run \
    # the only endpoint that exists
    --http-allow "POST api.openai.com/v1/chat/completions" \
    --http-deny  "* */admin/*" \
    # trust the ephemeral CA, no install step
    --http-inject-ca /etc/ssl/certs/ca-certificates.crt \
    # the key stays in the supervisor
    --credential openai=env:OPENAI_API_KEY \
    --http-auth "POST api.openai.com/v1/* bearer openai" \
    # filesystem and resource envelope
    -r /usr -r /lib -r /etc -w /work \
    -m 1G -P 32 -t 600 \
    -- python3 agent.py

Untrusted CI Builds

A pull request from a fork is untrusted code with a build script attached. The usual answers are a disposable VM per job, which is slow and expensive, or Docker on a shared runner, which means handing the job a socket that is equivalent to root.

Sandlock runs the build as an ordinary user with the network closed, the toolchain read-only, and the source tree copy-on-write. If the build succeeds the writes are committed; if it fails they are discarded. --dry-run goes further and shows you the exact set of files a build would touch without letting any of it land.

No root, no daemon, no Docker socket on the runner.
~5 ms of startup overhead, so per-step confinement is practical.
Reproducible builds. Freeze the clock, seed the PRNG, sort directory reads, and disable ASLR to remove the usual sources of nondeterminism.
Generated policies. sandlock learn observes a real build and emits a TOML profile of exactly what it touched.
Nesting

A sandboxed job can itself run Sandlock. The inner invocation uses --no-supervisor, since the kernel permits only one seccomp notification listener per task.

Build a fork's PR, offline and reversible 
# See what the build would change, change nothing
$ sandlock run --dry-run --workdir . \
    -w . -r /usr -r /lib -r /bin -r /etc \
    -- make build
A  build/out.o
M  Cargo.lock

# Run it for real: no network, capped, COW-committed
$ sandlock run --workdir . \
    -w . -r /usr -r /lib -r /bin -r /etc \
    -m 4G -P 64 -t 1800 \
    -- make -j4

# Deterministic: frozen clock, seeded randomness
$ sandlock run \
    --time-start "2000-01-01T00:00:00Z" \
    --random-seed 42 --deterministic-dirs \
    -- ./build.sh

Multi-Tenant Code Execution

Notebook backends, code interpreters, autograders, and evaluation harnesses all run one untrusted snippet per request, thousands of times a day. Container startup dominates the request; a pool of warm containers trades that latency for cross-request contamination.

A Sandlock sandbox starts in about 5 ms, so a fresh one per request is affordable. Port virtualization gives every sandbox its own port space, so a hundred tenants can each bind port 8080, and /proc/net/tcp inside a sandbox shows only that sandbox's own sockets.

Fresh sandbox per request, with no pool and no reuse.
Named sandboxes get a stable virtual hostname, so a reverse proxy can route by name to the real port.
Fleet introspection. sandlock ps lists what is running; sandlock inspect prints a live sandbox's effective policy as JSON or TOML.
Virtualized /proc. Set the visible CPU count and memory size a tenant sees.
At scale

COW fork initializes expensive state once, then forks clones that share memory copy-on-write: 1000 clones in about 530 ms, roughly 1,900 forks per second. Each clone inherits the full confinement.

Two tenants, same port, no collision 
$ sandlock run --name api.local --port-remap \
    --net-allow-bind 8080 \
    -r /usr -r /lib -r /etc -- python3 server.py &

$ sandlock run --name web.local --port-remap \
    --net-allow-bind 8080 \
    -r /usr -r /lib -r /etc -- python3 server.py &

$ sandlock ps
NAME          PID      UPTIME  CMD
api.local     12345        5m  python3 server.py
web.local     12346        3m  python3 server.py

$ sandlock inspect api.local --toml
$ sandlock kill web.local

Split-Trust Data Pipelines

Some stages of a pipeline need the sensitive data; the stages that transform it do not. Normally that separation is a convention enforced by code review. Sandlock makes it a property of the process.

Chain stages with the | operator, giving each stage its own independent sandbox configuration. Data flows between them through kernel pipes, so the downstream stage sees the bytes but never gains the ability to open the source.

Per-stage policy. The reader has the data path; the processor does not.
eXecute-Only Agents (XOA). A planner with no data access generates code; an executor with data access but no network runs it.
Map-reduce. Fork COW clones for the map phase, then pipe their stdout into a reducer running in a different sandbox with a different policy.
Python: reader has data, processor does not 
from sandlock import Sandbox

trusted = Sandbox(
    fs_readable=["/usr", "/lib", "/bin",
                 "/etc", "/opt/data"],
)
restricted = Sandbox(
    fs_readable=["/usr", "/lib", "/bin", "/etc"],
)

# restricted can never open /opt/data itself
result = (
    trusted.cmd(["cat", "/opt/data/secret.csv"])
    | restricted.cmd(["tr", "a-z", "A-Z"])
).run()

Compliance Audit and Virtual Filesystems

Some requirements cannot be met by any declarative policy. A regulated environment needs a guaranteed record of every file the guest read or wrote, and it has to be one the guest cannot evade. A data platform may need artifacts streamed to object storage as they are written, not collected after the process exits.

Handlers cover both. Your code runs inside the supervisor, registered on whichever syscalls you care about, and sees each call before the kernel acts on it. Because interception sits below the language runtime, an audit trail built this way cannot be routed around by ctypes, a raw syscall, or a rewritten import hook. Evading it would mean evading seccomp, which Sandlock blocks at the BPF level. Compare eBPF file tracing, which needs CAP_BPF and is often unavailable on managed Kubernetes.

Files with no host backing. Intercept openat and hand back a sealed in-memory file: a per-call config, a secret, a remote object.
Slow work without stalling. A handler doing a network round trip defers to a worker; the guest stays parked on that one call while everything else proceeds.
Confinement is never weakened. Built-ins run first, and a handler registered on a blocklisted syscall is rejected before fork rather than silently converting a kernel deny into an allow.
Rust, Python, or C. The same handler model is exposed through the C ABI, so any language that can call C can supply one.
Why it has to live here

The kernel allows one seccomp notification listener per process. Code that wants to intercept extra syscalls in the same sandbox must run inside the same supervisor loop, which is exactly what the handler API provides without forking Sandlock.

Python: deny by pattern, audit the rest 
import sandlock
from sandlock.presets import (
    AuditPathsHandler, PathDenyHandler, COMMON_PATH_SYSCALLS,
)

audit = AuditPathsHandler(
    callback=lambda path, _ctx: log.info("open %s", path)
)
deny = PathDenyHandler(deny=["*/.ssh/*", "*/.aws/*"])

sb = sandlock.Sandbox(
    fs_readable=["/usr", "/lib", "/etc"],
    fs_writable=["/work"],
)
sb.run_with_handlers(
    cmd=["python3", "task.py"],
    handlers=[(s, deny) for s in COMMON_PATH_SYSCALLS]
           + [(s, audit) for s in COMMON_PATH_SYSCALLS],
)

Hardened Workloads on Kubernetes

If your workloads already ship as OCI images, you do not have to rewrite anything to get Sandlock's confinement. sandlock-oci implements the OCI Runtime Specification command interface, so containerd, CRI-O, and the kubelet can drive it as a drop-in low-level runtime in place of runc.

The difference is what happens underneath. Where runc builds a container from namespaces, cgroups, and pivot_root, sandlock-oci produces a namespace-less container confined by Landlock and seccomp, running unprivileged. The OCI spec is translated by intent: memory and PID limits become resource caps, bind mounts become filesystem mappings, and linux.namespaces is ignored by design.

Drop-in. Accepts the runc flags containerd and CRI-O pass, including the ones that do not apply.
Checkpoint and restore a running sandbox to and from an image directory.
OCI 1.0.x, 1.1.x, and 1.2.x bundles; anything else is rejected at create rather than mis-mapped.
Drive a bundle directly 
$ sandlock-oci create mycontainer -b /path/to/bundle
$ sandlock-oci start  mycontainer
$ sandlock-oci state  mycontainer
$ sandlock-oci exec   mycontainer sh -c 'echo hello'
$ sandlock-oci kill   mycontainer SIGTERM
$ sandlock-oci delete mycontainer

# confirm the host kernel supports Landlock
$ sandlock-oci check
