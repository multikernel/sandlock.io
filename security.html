Security model

What Sandlock Guarantees, and What It Does Not

A sandbox is only useful if you know its edges. This page states the trust boundaries, the guarantees each layer provides, and the attacks that are explicitly out of scope.

Trust boundaries

Three Tiers of Trust

Sandlock's design principle is that the amount of trust placed in userspace should be as small as the policy allows.

Fully trusted

The host kernel

Landlock rules and the seccomp-bpf filter are evaluated by the kernel. If the kernel is compromised, so is every guarantee on this page. Sandlock shares a kernel with its workload, and that is the fundamental limit of the model.

Partially trusted

The supervisor

Runs in the parent process, outside the sandbox. It decides on the syscalls the kernel hands it: destination IPs, resource accounting, COW writes. Its handler chain is fixed, with built-ins first, so a custom handler can extend confinement but never relax it.

Untrusted

The workload

Assumed hostile. It never executes an unconfined instruction: NO_NEW_PRIVS, Landlock, and the seccomp filter are all installed before exec, and inherited descriptors above stderr are closed first.

Scope

In Scope and Out of Scope

Sandlock defends against

  • Filesystem escape. A confined process can only open paths reachable through the granted Landlock rules. Denied paths override broader grants, and grants are recursive so there is no gap to walk through.
  • Unapproved network egress. Default-deny. With no rules, every TCP connect is refused by Landlock, and UDP, ICMP, and raw socket creation are refused at the seccomp layer.
  • Data exfiltration to an approved host on an unapproved path. HTTP rules match method, host, and path, so an agent permitted to call one endpoint cannot repurpose the connection.
  • Credential theft by the workload. The secret lives in the supervisor and is attached in the proxy after the ACL check. With env: sources, the variable is stripped from the child's environment.
  • Privilege escalation via setuid. NO_NEW_PRIVS is set before the filter, so a setuid binary confers nothing.
  • Reaching sibling processes. Landlock's ABI v6 scopes deny abstract UNIX socket connections and signals to processes outside the sandbox.
  • Resource exhaustion of the host. Memory, concurrent processes, open files, CPU percentage, and COW disk usage are all capped.
  • Unintended writes. Copy-on-write stages writes in an upper layer, committed on success and discarded on error, so a failed run leaves the tree untouched.

Sandlock does not defend against

  • Kernel vulnerabilities. The workload runs on your kernel. A privilege-escalation bug in a syscall the policy permits defeats the sandbox. This is the price of not using a hypervisor.
  • Hardware side channels. Spectre-class attacks, cache timing, and other microarchitectural leaks are out of scope. CPU pinning reduces sharing but is not a mitigation.
  • A policy that grants too much. --net-allow '*' permits any destination; -w / grants the filesystem. Sandlock enforces the policy you wrote, not the one you meant.
  • A hostile supervisor host. If an attacker already controls the process that launches Sandlock, they control the policy.
  • Denial of service against itself. A workload can spin, thrash, or wedge on its own limits. Limits protect the host, not the workload's own progress.
  • Open-file limits as confinement. max_open_files is enforced with RLIMIT_NOFILE. A sandbox launched by root or with CAP_SYS_RESOURCE can raise it again; treat it as a budget, not a boundary.
  • Covert channels between sandboxes. Two sandboxes on the same host share timing, disk, and memory bandwidth.
  • Packet crafting needs. Raw ICMP sockets are never exposed, by design. This is a deliberate reduction in capability, not an oversight.
Design detail

Time-of-Check to Time-of-Use

Seccomp user notification has a well-known hazard, documented in seccomp_unotify(2): after the supervisor returns a continue verdict, the kernel re-reads any argument the syscall passed by pointer. A supervisor that inspects a path string and then allows the call has validated a string the workload is free to overwrite in the interval. Filtering on path strings in userspace is therefore unsound, no matter how carefully it is written.

Sandlock addresses this in two ways rather than papering over it.

Path strings are never exposed to policy callbacks

Policy events carry the syscall name, category, PID, network destination, and argv, but never a path. Path-based access control belongs in static Landlock rules, where the kernel resolves the path itself at access time and no window exists. For decisions that genuinely have to be made at runtime, the policy context offers deny_path() and allow_path(), which add Landlock-side restrictions rather than filtering strings.

argv is exposed, and it is made safe first

Command lines are too useful to withhold, so Sandlock makes them safe instead. Before exposing argv for an execve, the supervisor freezes every task in its process index, including peer processes that could alias the argv memory through a shared mapping. While a policy callback is active, fork-like syscalls are traced for one creation event so that children are registered before they can run user code.

If the freeze or the creation tracking cannot be established, for instance because a YAMA policy blocks ptrace, the syscall is denied with EPERM. The safety invariant is never silently relaxed in favour of letting the workload proceed.

Defaults

Strict by Default, Explicit to Weaken

Sandlock starts from deny and requires you to open things up. This matters because the failure mode of a permissive default is silent: nothing breaks, and you learn about the gap from an incident rather than from an error.

Network

With no network rules, Landlock denies every TCP connect, and UDP, ICMP, and raw socket creation are denied at the seccomp layer. Protocol availability follows rule presence: no UDP rule means UDP sockets cannot be created at all. Unrestricted egress requires writing --net-allow '*' explicitly, and ICMP still needs its own icmp:// rule on top of that.

Filesystem

With no filesystem rules, nothing is readable or writable beyond what the process already holds open. There is no implicit grant for /usr, /lib, or anything else, which is why every example on this site names them.

Syscalls

The default blocklist is applied unconditionally and cannot be turned off. A policy can add denials on top of it. Re-enabling is limited to named groups such as System V IPC, and unknown group names are rejected rather than ignored, so a typo fails loudly.

Missing kernel protections

By default Sandlock enforces every Landlock protection the host supports and refuses to start when a protection it expects is unavailable. Waiving one is a per-protection, explicit decision: allow_degraded enforces it where the kernel supports it and skips it where it does not, and disable turns it off outright. The resolved posture is part of a sandbox's checkpoint, so a restored sandbox comes back with the protections it was built with, not the ones the new host happens to offer.

sandlock check reports the host's Landlock ABI and per-protection availability before you deploy.

Secrets

Credential Handling

The point of credential injection is that a workload can use a secret without ever holding it. The secret is loaded into the supervisor from an environment variable, a file, or a file descriptor, and attached to a matching outbound request inside the proxy, strictly after the ACL check has passed. A request the policy would reject never gets the credential attached to it.

Three properties are worth stating plainly:

The child does not carry the value. With an env: source, the variable is stripped from the child's environment, so a compromised agent cannot read its own key back. With fd:, the secret never touches disk at all.

Cleartext HTTP is a warning, not a silent failure. Attaching a credential over plain HTTP sends it to the upstream in the clear. Sandlock emits a one-per-run warning rather than pretending the transport is safe.

The MITM CA's private key stays in memory. With --http-inject-ca, Sandlock generates an ephemeral CA whose private key is never written to disk, and splices only the public certificate into the trust bundles you name, at open time.

Sandlock deliberately ships no secret-manager client. An external fetcher materializes the value into a file: or fd: source, which keeps it off ps, out of shell history, and out of the child's environment, and lets you use Vault, a cloud secret store, or a CSI driver without Sandlock having an opinion.

Disclosure

Reporting a Vulnerability

If you believe you have found a way to escape a Sandlock policy, we want to hear about it before anyone else does.

Email contact@multikernel.io with a description and, where possible, a reproducer. Please do not open a public issue for a suspected escape until we have had a chance to respond.
