Comparison

Where Sandlock Fits

Sandlock is not a container runtime with a smaller footprint, and it is not a lightweight VM. It occupies a different point entirely: strict, kernel-enforced confinement of a process, with no image, no privilege, and no boot.

Adjacent tools

How It Compares to the Neighbours

Sandlock overlaps with several well-established tools. Here is where the overlap ends.

gVisor

Different boundary, different cost

gVisor puts a userspace kernel between the workload and the host, implementing the Linux syscall surface itself. That is a genuinely strong boundary, and it is the right answer when you need to run a full untrusted operating-system image.

The cost is that every syscall is serviced by the Sentry, and application compatibility depends on how completely the Sentry reimplements the interface. Sandlock leaves the host kernel in the syscall path and only intercepts the small set of calls that carry policy decisions, which is why a Redis workload keeps 97% of its bare-metal throughput.

bubblewrap and firejail

Same spirit, different mechanism

These build a confined view of the system out of mount, PID, and user namespaces. They are unprivileged (given user namespaces) and fast, and for desktop application sandboxing they are excellent.

Sandlock differs in that the policy is an access-control ruleset rather than a constructed namespace, so there is no filesystem to assemble and no user-namespace requirement. It also covers ground namespaces do not: destination-IP allowlisting, HTTP method and path rules, credential injection, copy-on-write commit and rollback, and a programmable per-syscall policy callback.

seccomp filters you write yourself

The layer below

A hand-written seccomp-bpf filter is precise and free, and Sandlock uses exactly that as one of its layers. What a raw filter cannot do is inspect arguments that live behind a pointer, because the kernel re-reads user memory after the filter runs.

That is why path-based decisions belong in Landlock and destination-based decisions belong in the supervisor, where the socket can be duplicated and inspected safely. Sandlock's job is to assemble these pieces so the combination is sound rather than plausible-looking.

Kubernetes with runc

Not either/or

If your workloads already ship as OCI images, Sandlock does not ask you to leave that behind. sandlock-oci implements the OCI runtime interface, so containerd, CRI-O, and the kubelet can drive it in place of runc.

What changes is the enforcement: the result is a namespace-less, cgroup-less container confined by Landlock and seccomp, running unprivileged. See the OCI runtime guide for the spec translation table.

Honest limits

When Sandlock Is the Wrong Tool

Picking the wrong isolation primitive is worse than picking none, because it buys confidence you have not actually earned. These are the cases where you should reach for something else.

You need a separate kernel

Sandlock's workload runs on your kernel. A kernel-level vulnerability is a shared risk. If your threat model includes an attacker who will spend a kernel exploit on you, use a hypervisor boundary: a microVM, or Multikernel's per-workload kernel architecture.

You need to boot a system

Sandlock confines processes, not machines. If the thing you are running expects init, systemd, a full device tree, or its own kernel modules, a VM is the correct abstraction and Sandlock will fight you.

Your kernel is older than 6.12

Landlock ABI v6 lands in 6.12, and the strict default refuses to start without the protections it expects. Individual protections can be degraded or disabled per policy, but each one you waive is confinement you no longer have.

You need hard CPU or memory guarantees

Limits are enforced by the supervisor rather than by cgroups: memory by tracking allocation syscalls, CPU by cycling SIGSTOP and SIGCONT. That is a budget, and a good one, but it is not the scheduler-level guarantee a cgroup gives you.

You are not on Linux

Landlock and seccomp are Linux facilities. There is no macOS, BSD, or Windows port, and there will not be one, because the entire design rests on these two kernel interfaces.

You need dynamic, rotating secrets

Credential injection loads the secret once at supervisor start. A leased or rotating value is picked up only on the next run. Sandlock composes with a secret manager rather than embedding one.
